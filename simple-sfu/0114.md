**1）H264 / VP8 / VP9 区别**
- **阵营/授权**：H264（专利/授权较多，历史上 WebRTC 里兼容性最好的一批），VP8/VP9（Google 推的开放阵营，VP9 压缩更强）。
- **压缩效率**：一般 **VP9 > H264≈VP8**（同等画质下 VP9 更省带宽，但更吃编码算力/更容易触发硬件差异）。
- **硬件加速**：H264 在硬件编码/解码覆盖面通常最好；VP9 新设备也不少，但整体仍更“看设备/浏览器版本”。
- **WebRTC 兼容性**：VP8 是 WebRTC 世界里很“稳”的默认选项；H264 在很多场景也很稳；VP9 更看你链路和算力预算。
- **你这个项目里**：服务端用 `RegisterDefaultCodecs()`，浏览器/推流端最终用哪个编码取决于 SDP 协商结果（两边共同支持的 codec）。

**2）为什么 F12 看不到视频流/数据流**
- **WebRTC 媒体不走“普通网络请求”**：音视频走 SRTP/ICE 的 UDP 通道，不会在 Network 面板里像 XHR/Fetch 那样显示为一条“视频流请求”。
- **正确入口**：
  - Chrome/Edge：打开 `chrome://webrtc-internals/`（或 `edge://webrtc-internals/`）看 ICE、码率、丢包、编码、candidate 等。
  - 也可在 Console 里看 `pc.getStats()`（你前端如果加了 stats 输出，就能看到 bytes/packets/fps）。
- **你能在 F12 Network 里看到的**：通常只有信令用的 HTTP（offer/answer 的 POST）或 websocket（如果你做了 trickle）。

**3）是否支持双工通信（拉流端给推流端发消息）**
- **支持，但你当前实现没做**：WebRTC 的双工通常靠 **DataChannel**（pc.CreateDataChannel / OnDataChannel），可以在“拉流端 ↔ 服务端 ↔ 推流端”之间转发消息。
- **注意拓扑**：你这个是 SFU 结构，推流端和每个拉流端是**不同的 PeerConnection**，所以“拉流端发给推流端”需要你在服务端把 DataChannel 消息做一次路由/转发（类似聊天室）。
- **现状**：当前代码主要是“一个发布者媒体 → 多个订阅者媒体”，没有 DataChannel 的建立与转发逻辑。

**5）支持多个推流端吗？为什么 NAT 1:1 不是主流？**
- **多个推流端：当前不支持（或说没有设计好）**  
  你现在是“全局只有一个 `localTrack` / `publisherPC`”的模型：新的推流会覆盖旧的，订阅者也只订阅这一条全局 track。要支持多个推流端，通常要引入：
  - “房间/流 ID → publisherPC + 一组 tracks”的映射
  - subscribe 时指定要订阅哪个 stream/room
  - 以及并发安全、生命周期清理
- **NAT 1:1 为什么不主流**：它是“能用但场景有限”的工程捷径。
  - 只有在你确实有**公网 IP 与实例 1:1 映射**、且网络路径允许 UDP 打洞/直连时才理想。
  - 一旦遇到企业网/对称 NAT/严格防火墙，还是得靠 TURN 中继；云厂商/企业环境里这类情况很常见。
  - 主流做法通常是：**ICE(STUN) + 必要时 TURN**，再配合合理的端口策略/防火墙规则/多地域部署，覆盖面更广。
- **你现在用 NAT 1:1 的原因**：是为了解决“外部访问不到 candidate/无法 STUN”的现实约束，让单机/单发布者先跑通；它更像“部署策略”，不是 WebRTC 的最佳实践通用解。
